# ADR-20260722-001 — Multi-Tenant Core/Tenant Architecture

| Campo | Valor |
|-------|-------|
| **ID** | `ADR-20260722-001` |
| **Fecha** | 2026-07-22 |
| **Spec** | `SPEC-20260722-001` |
| **Estado** | proposed |

## Context

El repo `sonora-digital-corp/` mezcla lógica de motor (core) con datos de clientes en un solo plano sin fronteras claras:

- `clients/` contiene proyectos completos de clientes (abe-music, azrec, el-joyero, mds-corp, nathy-conta, r1) como workspaces independientes, no como configuraciones parametrizables de un core compartido
- `config/tenants.yaml` y `config/tenants.json` definen tenants pero no hay un loader runtime que aísle contexto por tenant
- `core/` tiene lógica que indirectamente referencia a clientes
- No existe un directorio `tenants/` como frontera explícita de aislamiento
- Las skills de OpenClaw (ClawHub) están disponibles globalmente sin control por tenant
- Qdrant usó una sola colección (`sdc_knowledge`) para múltiples tenants

Esto impide:
- Escalar a nuevos clientes sin copiar/pegar proyectos enteros
- Asegurar aislamiento de datos entre clientes (Qdrant, Neo4j, Postgres)
- Vender la plataforma como producto SaaS multi-tenant
- Actualizar el core sin arriesgar configuraciones de clientes
- Aplicar políticas de seguridad diferenciadas por cliente

## Decision

1. **Refactorizar el repo existente** (no crear mystic-core/ separado) manteniendo un solo historial git y CI/CD
2. **Crear directorio `tenants/`** con subdirectorios por cliente: `astrotech/`, `sonora-digital/`, `abe-music/`, `_template/`
3. **Extraer capa Core agnóstica**: `core/` no debe contener strings hardcodeados de clientes
4. **Cada tenant define en archivos YAML/MD estandarizados**: `prompt.md`, `branding/`, `knowledge/`, `memory/`, `skills/`, `tools.yaml`, `mcp.yaml`, `policies.yaml`, `workflows/`, `config.yaml`
5. **El Core carga dinámicamente** el TenantContext en runtime según `tenant_id`
6. **Aislamiento en DBs**: Qdrant colecciones por tenant (`tenant_{id}_memory`), Neo4j databases por tenant, Postgres RLS por tenant
7. **Skills como archivos markdown**: OpenClaw carga skills dinámicamente; skills del core global no se inyectan en tenants que no las tienen permitidas en `tools.yaml`
8. **Deprecar `clients/`** migrando cada proyecto a `tenants/` y archivando lo viejo en `archive/clients/`
9. **Crear gateway/ como capa de entrada**: webhooks, auth, rate limiting por tenant

## Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **Refactor monorepo (elegido)** | Un solo git, CI/CD compartido, migración gradual, historial unificado | Ruido de refactor en git history |
| `mystic-core/` repo separado | Core vendible como producto standalone, límite arquitectónico neto | Dos repos que sincronizar, CI/CD duplicado, ruptura abrupta con código actual |
| Mantener estructura actual | Cero trabajo inmediato | No escala, riesgo de fuga de datos entre clientes, onboarding manual |

## Consequences

- **Positivas**: Aislamiento real entre clientes a nivel de código + DB
- **Positivas**: Onboarding de nuevos clientes en minutos (copia de `_template/`)
- **Positivas**: Core actualizable sin tocar configuraciones de tenants
- **Positivas**: Se puede vender la plataforma como SaaS multi-tenant
- **Trabajo**: Migrar `clients/` → `tenants/`, estandarizar configs, crear TenantResolver
- **Trabajo**: Segmentar Qdrant/Neo4j/Postgres por tenant
- **Riesgo**: Refactor puede afectar estabilidad si no se hace por fases con feature flags

## Lessons

- La estructura de carpetas ES la arquitectura — si los directorios no reflejan el modelo mental (Core vs Tenant), el código tampoco
- Ya existían `config/tenants.yaml` y `config/tenants.json` como proto-tenants, pero no había aislamiento real
- OpenClaw + skills como markdown es el patrón correcto: un motor único con personalidades intercambiables por tenant
- No intentar abstraer demasiado pronto; la separación Core/Tenant es la frontera natural
