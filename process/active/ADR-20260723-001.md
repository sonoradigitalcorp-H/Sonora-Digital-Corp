## Context

Necesitamos crear una página pública interactiva que demuestre agentes de IA como un sistema de galaxias 3D. Las decisiones arquitectónicas deben balancear impacto visual (para ventas), funcionalidad (onboarding + voz), y mantenibilidad (multi-tenant, reusable).

---

## Decision 1: Three.js para visualización 3D de la galaxia

### Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **Three.js + React Three Fiber** | Ecosistema maduro, R3F simplifica React, drei incluye helpers orbitales, gran comunidad, buen rendimiento | Curva de aprendizaje para shaders personalizados, bundle size ~200KB |
| Babylon.js | Más integrado, mejor tooling nativo | Menor comunidad React, menos ejemplos de galaxias |
| Spline | No-code, rápido prototipar | Limitado para interacciones dinámicas, lock-in vendor, costo |
| Pure WebGL (sin librería) | Control total, mínimo bundle | Complejidad extrema, tiempo de desarrollo 5x mayor |
| CSS 3D transforms | Sin dependencias JS, ligero | Limitado a transformaciones básicas, no soporta partículas/galaxias reales |

### Decision

**Three.js + React Three Fiber + drei** para el prototype.

### Consequences

- Bundle size aumentado (~200KB Three.js + R3F + drei) — acceptable para demo
- Necesitamos optimizar texturas para mobile (auto-detectar y reducir resolución)
- Shaders personalizados para efecto galaxia (partículas orbitales) requerirán aprendizaje
- Alternativa: si el bundle es problemático, considerar load-on-demand (dynamic import)
- Fallback 2D obligatorio para navegadores sin WebGL (detectar con WebGLRenderingContext)

### Lessons

- Three.js es el estándar de facto para 3D web — mejor inversión a largo plazo
- R3F nos permite usar componentes React familiares en lugar de imperativo WebGL
- El efecto galaxia puede lograrse con particle systems + orbit controls sin shaders complejos inicialmente

## Decision 2: FastAPI + WebSocket para backend y STT/TTS streaming

### Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **FastAPI + WebSocket** | Async nativo, type hints, auto-docs, WebSocket para streaming real-time, integra bien con Python ML/STT | Requiere manejo manual de conexiones WebSocket, scaling horizontal necesita Redis pub/sub |
| Flask + HTTP | Simple, conocido | No nativo async, streaming más complejo, menos performante |
| Express.js (Node.js) | Async, buen ecosistema WebSocket | Duplica stack (ya usamos Python para SDC core), separa lógica |
| Django + Channels | Full-featured, ORM incluido | Overkill para prototype, más complejo de configurar |
| Go + Gorilla WebSocket | Máximo rendimiento, concurrencia nativa | Nuevo lenguaje para el equipo, ecosistema STT/TTS más limitado |

### Decision

**FastAPI + WebSocket** para el backend del prototype.

### Consequences

- FastAPI reutiliza el stack Python de SDC core — consistencia de equipo
- WebSocket necesario para streaming de audio STT/TTS en tiempo real
- Para prototype: conexiones WebSocket directas (sin Redis pub/sub)
- Para production: necesitar Redis pub/sub para scaling horizontal de WebSocket
- SQLite como database del prototype — migrar a Postgres cuando scale criteria se cumplan
- JSONL para events — suficiente para prototype, Postgres events table para production

### Lessons

- Mantener stack consistente (Python/FastAPI) reduce complejidad operativa
- WebSocket streaming requiere manejo cuidadoso de reconexión y estado
- Separar claramente las capas: API routes → services → models → db

## Decision 3: Multi-tenant data isolation via tenant_id keying

### Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **tenant_id como clave de aislamiento (row-level)** | Simple, un solo schema, fácil de migrar a Postgres con RLS después | Requiere discipline en cada query (never forget tenant_id filter), riesgo de data leak si bug |
| Schema-per-tenant | Aislamiento total, sin riesgo de cross-tenant data leak | Complejidad de migración alta, N schemas = N× mantenimiento, no escala |
| Database-per-tenant | Máximo aislamiento, compliance fácil | Costo infraestructura alto, overkill para prototype |
| Redis + SQLite hybrid | Redis para sessiones rápidas, SQLite para persistencia | Complejidad operativa, dos sistemas que mantener |

### Decision

**tenant_id como clave de aislamiento** para prototype. Cada query, cada operación, cada evento incluye tenant_id como filtro obligatorio.

### Consequences

- Todos los modelos Pydantic incluyen tenant_id como campo requerido
- Todos los queries de base de datos filtran por tenant_id
- Middleware FastAPI inyecta tenant_id desde auth token/session
- Para production: migrar a PostgreSQL Row Level Security (RLS) para aislamiento garantizado por DB engine
- Tests deben verificar que tenant A nunca puede acceder datos de tenant B
- Engram memory keyed por tenant_id para aislamiento de memoria

### Lessons

- Row-level isolation es el approach más pragmático para prototype
- El riesgo de data leak es real — tests de aislamiento son mandatory
- PostgreSQL RLS resuelve este problema completamente en production
- Documentar explícitamente que este approach es provisional

## Decision 4: wacli + WhatsApp para pipeline de voz STT/TTS

### Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **wacli (WhatsApp CLI)** | Gratuito, no requiere WhatsApp Business API approval, funciona con WhatsApp Web | No oficial, puede break con updates de WhatsApp, rate limits no garantizados |
| WhatsApp Business Cloud API | Oficial, soporte Meta, SLA garantizado | Requiere business verification, costo por conversation, approval process lento |
| Twilio WhatsApp | Oficial, buen SDK, soporte | Costo por mensaje, setup más complejo, vendor lock-in |
| Telegram voice | Fácil de implementar, API limpia | No es WhatsApp (usuario prefiere WhatsApp), menor adopción en LATAM |
| WebRTC directo | Control total, sin intermediarios | Complejidad alta (signaling, STUN/TURN, mobile browsers), overkill |

### Decision

**wacli para prototype** con fallback a Telegram y web como alternativas. Documentar claramente que para production se necesita WhatsApp Business Cloud API.

### Consequences

- wacli puede fallar sin warning — necesito health checks periódicos
- Fallback automático a Telegram si WhatsApp no disponible
- Fallback a modo texto si STT/TTS no disponible
- STT: OpenAI Whisper API para prototype (pagar por uso), local Whisper para production
- TTS: ElevenLabs API para prototype (calidad), local TTS para production
- Pipeline debe ser configurable por tenant (elegir red social preferida)
- Events de voice_pipeline_error deben alertar al ops team

### Lessons

- wacli es suficiente para validar el concepto de voz
- La extracción a cualquier red social es un feature importante — el usuario elige
- Para production real, WhatsApp Business API es mandatory (confiabilidad + compliance)
- El pipeline STT/TTS debe ser abstraído — provider swap sin cambiar lógica de negocio
