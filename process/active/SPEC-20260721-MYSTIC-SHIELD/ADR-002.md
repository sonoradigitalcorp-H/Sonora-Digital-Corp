# ADR-20260721-002 — Pipeline Sincrónico (MVP) vs Asíncrono con Cola

| Campo | Valor |
|-------|-------|
| **ID** | `ADR-20260721-002` |
| **Fecha** | 2026-07-21 |
| **Spec** | `SPEC-20260721-MYSTIC-SHIELD` |
| **Estado** | aceptado |

---

## Context

El pipeline de diagnóstico ejecuta 6 pasos secuenciales:
1. Escanear red (ping sweep ~2-60s)
2. Analizar con LLM (OpenRouter ~5-15s)
3. Generar PDF (fpdf2 ~5s)
4. Generar audio (edge-tts ~10-20s)
5. Enviar WhatsApp (wacli ~5-10s)
6. Enviar Email (smtplib ~2-5s)

Esto suma ~30-120s por diagnóstico. Con N clientes simultáneos, el tiempo escala linealmente.

---

## Decision

**MVP: Pipeline sincrónico (bloqueante).** El usuario llama a `shield_diagnose()` y espera el resultado completo.

**Motivación:** 
- Simplicidad total: sin Redis, sin colas, sin workers
- Para MVP con 1-5 clientes, 2 minutos de espera es aceptable
- El CEO no espera en línea — recibe WhatsApp cuando termina
- Se puede migrar a async cuando haya >10 clientes

**Futuro (post-MVP):** n8n + Redis queue. El endpoint `/api/diagnose` encola el job y regresa un `diagnosis_id`. Un worker MCP procesa la cola. El CEO recibe notificación cuando termina.

---

## Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| **A. Sync (MVP)** | Simple, 0 infra adicional, debug fácil | Bloqueante, no escala >10 clientes |
| **B. Async con Redis + n8n** | Escalable, no bloquea | Infra adicional, más complejo |
| **C. Async con Celery** | Maduro, robusto | Overkill para MVP |

---

## Consequences

- MVP: shield_diagnose() async pero pipeline secuencial
- El timeout de httpx es 60s (suficiente para LLM + subprocesses)
- Si un paso falla (ej: OpenRouter), el pipeline continúa con fallback
- Migrar a async requiere: Redis, worker service, n8n workflow, polling endpoint

---

## Lessons

- El paso más lento es ping sweep (2-60s según subnet) y edge-tts (10-20s)
- OpenRouter a veces falla con 'choices' — tener fallback template listo
- wacli manda los mensajes aunque el websocket esté desconectado
