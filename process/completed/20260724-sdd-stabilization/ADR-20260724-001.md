---

## Context

El sistema SDC crecía sin un framework de desarrollo unificado. Cada capability se implementaba con patrones distintos, sin tests consistentes, sin ADRs, sin agent registry. La falta de estandarización generaba deuda técnica y dependencia del fundador para interpretar el sistema.

---

## Decision

Adoptar SDD (Spec-Driven Development) como framework único de desarrollo. Incluye:
1. CLI `sdd` para ciclo spec→plan→tasks→implement
2. 7 speckit skills en OpenClaw para orquestación conversacional
3. Agent registry YAML como SSOT de capacidades autónomas
4. Structural evals (5 dominios, 341 tests) para garantizar integridad
5. Event system (bridge → notifier → handlers) para desacoplamiento
6. Gherkin BDD (35+ features) como especificación ejecutable
7. Integration tests reales contra Neo4j + ComfyUI
8. Redteam evals para seguridad adversarial

---

## Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| A: SDD Framework (elegida) | Unificado, reusable, automatizable, documentado | Curva de aprendizaje inicial |
| B: Continuar sin framework | Sin inversión inicial | Deuda técnica, inconsistencias, dependencia fundador |
| C: Adoptar TDD puro | Simple | Sin contexto de negocio, sin ADRs, sin agent registry |

---

## Consequences

- Toda capability nueva debe pasar por SDD pipeline
- 69 archivos nuevos/modificados (2557 insertions)
- 20 ADRs históricos documentados retroactivamente
- 9 integration tests que requieren Neo4j + ComfyUI activos
- Redteam config permite evaluaciones de seguridad continuas
- Costo: ~2h por capability nueva en setup de spec + gherkin

---

## Lessons

- SDD pipeline reduce significativamente el time-to-first-test
- Agent registry obliga a pensar en capacidades antes de implementar
- Structural evals detectaron 12 inconsistencias en skills/documentación
- BDD tests con pytest-bdd son más legibles que asserts tradicionales
