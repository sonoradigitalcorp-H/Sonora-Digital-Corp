## 1. Objetivo

Estabilizar el framework SDD (Spec-Driven Development) con ADRs, unit tests, structural evals, gherkin BDD, agent registry, speckit skills, notifier worker, OpenClaw bridge, integration tests reales contra Neo4j/ComfyUI, y redteam config.

---

## 2. Value Driver

**Automation / Knowledge / Founder-Independence**

- SDD framework reusable para toda capability futura
- BDD tests automatizados validan spec compliance
- Structural evals garantizan integridad del sistema
- Agent registry como SSOT de capacidades autónomas
- Notifier worker desacopla eventos de acciones
- Integration tests reales contra infraestructura activa

## 7. Technical Approach

### Arquitectura

```
[sdd CLI] → spec-new → process/active/SPEC-*.md
          → test     → pytest tests/gherkin/ + tests/unit/
          → eval     → pytest evals/structural/

[OpenClaw] → /speckit.* → Skills → spec → plan → implement

[Agents] → registry.yaml → capabilities + cost_tier
         → agents activos en 4 tipos: data-ingestion, cognitive, creative, business, system

[Events] → bridge.py → notifier.py → systemd service
         → handlers/ → listener.py → run_listener.py

[Tests] → tests/gherkin/ → 35+ .feature files
        → tests/steps/ → step definitions (pytest-bdd)
        → tests/integration/ → 9 tests (Neo4j + ComfyUI)
        → evals/structural/ → 341 tests (5 domains)
        → evals/redteam/ → 40+ adversarial prompts
```

## 10. Kill Criteria

- SDD CLI no funcional después de 3 intentos de fix
- Redteam reveal vulnerabilidad crítica no mitigable
- Integration tests destruyen datos de producción

---

## 11. Scale Criteria

- **>20 capabilities**: auto-generar specs desde índice yaml
- **>50 agents**: migrar registry a base de datos
- **>1000 tests**: parallelizar con pytest-xdist
- **>5 services monitoreados**: notifier → alertmanager
