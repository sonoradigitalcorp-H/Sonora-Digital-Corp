---

## Context

Mystic Voice necesitaba memoria persistente entre sesiones, monitoreo del sistema en vivo, alertas proactivas de CPU/RAM, instalación como app de escritorio, y wake word automática. Se requería una arquitectura simple que funcionara sin depender de infraestructura externa (Postgres, MCP Gateway).

Existía un MCP Gateway para Engram pero agregaba latencia innecesaria para voice realtime. La sesión debía sobrevivir recargas de página y reconexiones WebSocket.

---

## Decision

### 1. SQLite como persistencia principal (no Postgres/Redis)

- `state/mystic_sessions.db` con WAL mode y thread-safe lock
- Esquema: `sessions` (id, user_id, history JSON, context JSON) + `interactions` (cada turno)
- Auto-recovery en caso de corrupción (borra y recrea)
- Fallback sí funciona: si SQLite falla, el asistente sigue funcionando sin persistencia

### 2. Direct Engram Bridge (no vía MCP Gateway)

- `EngramBridge` conecta directo a `state/engram.db` usando `core/engram.Engram`
- Capas: layer=1 (task) para interacciones individuales, layer=2 (project) para resúmenes de sesión
- MCP Gateway se usa como fallback no crítico (try/except silencioso)
- Reduce latencia ~200-500ms vs MCP Gateway round-trip

### 3. Kokoro TTS como provider primario

- `provider="kokoro", voice="em_alex"` en el servidor
- Genera archivos MP3 temporales en `/tmp/`, servidos vía `/api/audio/`
- Sin dependencia externa (corre local)

### 4. Proactive Monitor Loop

- Tarea asíncrona `_proactive_monitor_loop()` cada 30s
- Notifica a TODAS las sesiones activas vía WebSocket
- No intrusivo: solo alerta visual (no interrumpe con voz)

### 5. 3-tier LLM fallback

1. OpenRouter (`openai/gpt-4o-mini`) — principal
2. OpenCode API — fallback
3. Ollama local (`qwen3:4b`) — último recurso

---

## Options Considered

| Opción | Pros | Contras |
|--------|------|---------|
| A. SQLite local | Simple, zero infra, auto-recovery built-in | Sin concurrencia real, single file point of failure |
| B. Postgres en Docker | Escalable, concurrente | Dependencia externa, overhead para asst personal |
| C. Redis Streams | Rápido, pub/sub nativo | Datos volátiles, sin SQL queries, complejidad adicional |
| D. MCP Gateway para Engram | Capa de abstracción, multi-tenant | Latencia extra 200-500ms, single point of failure |

Se eligió A (SQLite) por simplicidad y porque el scale criteria define migración a Postgres cuando >10 sesiones/día.

---

## Consequences

- Founder tiene memoria persistente sin infraestructura externa
- Si Engram DB se corrompe, solo se pierde la memoria de voz (no crítica)
- Kokoro TTS no requiere API key — zero cost operativo
- Proactive monitor envía a TODAS las sesiones — sin filtro por sesión
- `session_id` truncado a 8 chars — riesgo teórico de colisión (no crítico para caso de uso personal)
- Fallback 3-tier asegura que Mystic nunca se queda sin respuesta
- Enfram bridge duplica lógica de MCP client — refactor futuro necesario

---

## Lessons

- SQLite WAL mode + RLock es suficiente para asst personal de 1 usuario
- Direct Engram bridge es 3x más rápido que MCP Gateway para voice realtime
- El patrón `_safe()` en monitor.py (try/except graceful) debe replicarse en todos los skills que dependan de librerías opcionales
- Kokoro TTS local elimina dependencia de API externa — ideal para Founders Independence
- Proactive monitor loop es simple pero efectivo — extender a más métricas (disk, network) en futura iteración
